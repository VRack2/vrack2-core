## Что такое vrack2-core

`vrack2-core` — это фреймворк: он предоставляет классы и правила, из которых вы собираете сервис и запускаете его.

Идея простая: структура сервиса **описывается** в JSON, а не программируется. Из небольших самостоятельных блоков — **устройств** — вы собираете структуру: какие устройства нужны, с какими настройками и как они соединены. Фреймворк читает эту структуру и делает всю механику: создаёт устройства, проверяет настройки, соединяет порты, запускает и обслуживает в работе.

**Устройство** — это обычный JS-класс, наследующий `Device`. В нём описано:

- **опции** — настройки, которые вы задаёте при запуске (например, `scale: 2` для счётчика);
- **порты** (входы и выходы) — откуда устройство принимает данные и куда их отдаёт;
- **действия** (actions) — операции, которые устройство выполняет по запросу извне;
- **метрики** — числа, которые устройство записывает во время работы; служебный модуль кладёт их в базу данных;
- **жизненный цикл** — что устройство делает при старте и когда в него приходят данные.

**Соединение** — связь между портами устройств: она позволяет передавать данные от порта одного устройства к порту другого. Соединения указываются в `service.json` рядом с устройствами, по одной строке на связь: `Counter1.result -> Lamp1.on` читается как «выход `result` устройства `Counter1` передаёт данные во вход `on` устройства `Lamp1`».

## Пример: два устройства

Допустим, у вас два устройства:

- `Counter` — считает 1, 2, 3…: на каждый тик, который в него приходит, он увеличивает счёт (на шаг `scale`) и отдаёт новое значение на выход `result`;
- `Lamp` — принимает число на вход `on` и зажигает с этой яркостью.

Структура сервиса описывается в файле `service.json`:

```json
{
  "devices": [
    { "id": "Counter1", "type": "myvendor.Counter", "options": { "scale": 2 } },
    { "id": "Lamp1",    "type": "myvendor.Lamp",    "options": { "maxBrightness": 128 } }
  ],
  "connections": [
    "Counter1.result -> Lamp1.on"
  ]
}
```

Фреймворк берёт эту структуру и делает следующее:

1. **Находит классы устройств.** По `type: "myvendor.Counter"` находит файл `devices/myvendor/Counter.js` — там лежит код класса.
2. **Проверяет опции.** У `Counter` правило: «`scale` — целое число, не меньше 1». `2` — ок; `"x"` — запуск прервётся с понятной ошибкой.
3. **Создаёт** `Counter1` и `Lamp1`.
4. **Соединяет** выход `result` счётчика со входом `on` лампы: теперь на каждом тике счётчик сам шлёт лампе новое значение.
5. **Запускает** и начинает обслуживать: данные текут по соединениям, состояние сохраняется, события уходят наружу.

Ключевой момент: в коде `Counter` нет ни строчки про лампу — связь описана только в JSON. Хотите другую схему — меняете JSON, код не трогаете.

## Из чего состоит ядро

Внутри ядра четыре основных участника:

| Участник | Что делает |
|---|---|
| `MainProcess` | Точка входа: принимает id сервиса, его структуру и список служебных модулей, затем запускает всё по порядку. |
| `Bootstrap` | Подключает служебные модули (их называют **boot-классами** — объясним ниже). |
| `ServiceLoader` | Читает `service.json`: создаёт устройства, проверяет опции, соединяет порты. Умеет добавлять и удалять устройства уже в работающем сервисе. |
| `Container` | Хранит все устройства и их состояние; передаёт между устройствами и наружу события; выполняет действия (actions). |

**Boot-классы** — это просто служебные модули: сохраняют состояние устройств в файлы, пишут метрики в БД, сохраняют структуру сервиса. Своими можно заменить — устройства этого даже не заметят. Подробности — [07-Bootstrap](07-Bootstrap.md).

Порядок запуска:

```
MainProcess.run()
 ├─ Bootstrap     — подключить служебные модули
 ├─ ServiceLoader — создать устройства, проверить опции, соединить порты
 └─ Container     — запустить устройства (старт + асинхронная инициализация)
```

Полная последовательность с пояснениями — [01-Architecture](01-Architecture.md).

## Почему всё построено на событиях

Внутри ядра всё происходит **событиями**: «устройство отдало данные», «устройство попросило сохранить состояние», «устройство завершилось». Событие — это обычный JS-объект (`{ device, data, trace }`), который получают все, кто на него подписался.

Зачем так:

- **Служебные модули просто слушают.** Хранилище слушает «сохрани», метрики — «запиши метрику». Сменили файловое хранилище на базу данных — устройства не тронули.
- **Тесты.** События — обычные объекты: легко перехватить и проверить.
- **Независимость от среды.** Тот же сервис работает в процессе Node, в воркере или на другой машине — наружу всё уходит одними и теми же событиями.
- **Горячая перекомпоновка.** Устройства можно добавлять и убирать в работающем сервисе: состояние и так описано событиями, а структура сохраняется при каждом изменении.
